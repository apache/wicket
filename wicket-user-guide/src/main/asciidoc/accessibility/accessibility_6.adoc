Every function of the application must be operable from the keyboard (success criterion 2.1.1). With Wicket this mostly comes down to the element an AJAX component or behavior is attached to.

=== Links and buttons, not div and span

Browsers make two kinds of elements operable from the keyboard: links with an _href_ attribute and form controls such as _<button>_. They can receive focus with the Tab key, the Enter key activates a link, Enter and Space activate a button, and screen readers announce them as link or button. A _<div>_ or _<span>_ has none of this. An _AjaxEventBehavior_ on _click_ attached to a _<div>_ works with the mouse, but a keyboard user cannot reach it, and a screen reader user does not know it is there:

[source,html]
----
<!-- only for mouse users -->
<div wicket:id="details">Show details</div>
----

[source,java]
----
add(new WebMarkupContainer("details")
	.add(AjaxEventBehavior.onEvent("click", target -> showDetails(target))));
----

The same goes for an _AjaxLink_ attached to a _<div>_ or _<span>_: _AjaxLink_ adapts the tag only when it is an _<a>_ or a _<button>_. The solution is to attach the component to the element that matches what it does. An action on the current page, such as showing details, deleting an item or opening a dialog, is a button:

[source,html]
----
<button wicket:id="details">Show details</button>
----

[source,java]
----
add(new AjaxLink<Void>("details") {
	@Override
	public void onClick(AjaxRequestTarget target) {
		showDetails(target);
	}
});
----

On a _<button>_, _AjaxLink_ renders _type="button"_, so the button does not submit a form it is in. Navigation to another page or to another state that the user may want to bookmark is a link, and a plain _Link_ or _BookmarkablePageLink_ on an _<a>_ tag does it without AJAX at all. On an _<a>_ tag, _AjaxLink_ renders _href="#"_: the link can receive focus and is operable from the keyboard, but screen readers announce it as a link, which is not what users expect of an action.

Forms are submitted with _Button_, _AjaxButton_ or _AjaxSubmitLink_ on a _<button>_ or _<input type="submit">_. A form with such a button can also be submitted with the Enter key in a text field.

If a custom widget cannot be a native element, it needs everything the native element would have given it: a role (_role="button"_), a place in the tab order (_tabindex="0"_), a key handler for Enter and Space, and an accessible name. This is a lot of work to get right, and a _<button>_ styled with CSS is nearly always the better choice.

=== Events that change the context

Some AJAX behaviors react to events that the user does not intend as a command. A behavior on _focus_ runs when keyboard users merely tab through the page; it must not navigate, submit or open a dialog (success criterion 3.2.1). A behavior on _change_, such as _AjaxFormComponentUpdatingBehavior_ or _OnChangeAjaxBehavior_, runs every time the value changes: in a _<select>_ that is navigated with the arrow keys, that is for every option the user passes. Updating a part of the page, such as the cities for the selected country, is fine. Navigating to another page or submitting the form on a change is not, unless the user has been told before (success criterion 3.2.2); a separate button is the accessible way to do it.

Behaviors that react to _mousedown_ or _pointerdown_ run before the user can cancel the action by moving the pointer away (success criterion 2.5.2). The _click_ event, which _AjaxLink_ and _AjaxButton_ use, does not have this problem.

=== Dialogs and other widgets

A modal dialog takes the keyboard focus when it opens, keeps it inside while it is open and gives it back when it closes. _ModalDialog_ does this with _trapFocus()_, and _closeOnEscape()_ gives keyboard users a way out without searching for the close button (success criterion 2.1.2). The setup is shown in <<_focus_and_announcements_after_ajax_updates,paragraph 25.5>>.

For widgets such as tabs, trees and menus, the WAI-ARIA Authoring Practices (https://www.w3.org/WAI/ARIA/apg/[]) describe the roles and the keyboard interaction users expect. _TabbedPanel_ renders its tabs as a list of links, which is operable from the keyboard but does not implement the tabs pattern.
